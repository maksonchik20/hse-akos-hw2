# ИДЗ-2: умные цветы, вариант 14

Многопоточная программа на C11/POSIX для Linux. Основана на ИДЗ-1:
сохранены параметры, состояния цветов и одна стратегия FIFO.
Каждый цветок и садовник работает в отдельном потоке pthread.

## Сборка и запуск

Нужны C-компилятор, Make и Python 3 для тестов. Команды из папки проекта:

```sh
make
./build/smart-flowers
./build/smart-flowers --help
./build/smart-flowers --config configs/ordinary.conf --log ordinary.log
./build/smart-flowers --config configs/conflict.conf --log conflict.log
./build/smart-flowers --config configs/drought.conf --log drought.log
./build/smart-flowers --config configs/overwater.conf --log overwater.log
./build/smart-flowers --unlimited true --delay-ms 100
```

Последний запуск останавливается через Ctrl+C. Без аргументов: 3 цветка,
2 садовника, 40 тактов наблюдения. События и строка итогов `SUMMARY` идут
в терминал и журнал (`events.log` по умолчанию). Журнал перезаписывается.

| Конфигурация | Что показывает |
|---|---|
| ordinary.conf | Один цветок: заявка, полив, восстановление, новая заявка |
| conflict.conf | Восемь цветов и четыре садовника: конкуренция и параллельный полив |
| drought.conf | Один садовник не успевает обслужить все цветы |
| overwater.conf | Повторный полив внутри защитного интервала убивает цветок |

Порядок событий, победитель конфликта и итоговые счётчики зависят от планировщика.
Конфликт появляется, только если несколько садовников действительно выбрали
одну заявку; его наличие в конкретном запуске не гарантировано.

Пример итога `ordinary.conf` из сохранённого проверочного запуска:

```text
SUMMARY reason=time_limit time=20 created=3 completed=3 cancelled=0 pending=0 assigned=0 waterings=3 conflicts=0 overwater=0 dried=0 alive=1 invariants=ok
```

## Параметры

Синтаксис: `--имя значение`. Конфигурация: строки `имя=значение`, комментарии `#`.
Приоритет: значения по умолчанию < файл < командная строка.

| Параметр | По умолчанию; диапазон |
|---|---|
| flowers, gardeners | 3 и 2; 0…1000 |
| dry-rates, speeds | 1; числа 1…1000000 |
| request-threshold, death-threshold | 10 и 30; 1…1000000, первый меньше второго |
| water-duration, recovery-duration | 2 и 3; 1…1000000 тактов |
| protection-interval, duration | 5 и 40; 0…1000000 тактов |
| delay-ms | 0; 0…60000, при 0 один такт длится 10 мс |
| unlimited | false; true или false |
| log | events.log; путь к обычному файлу |

Скорости задаются одним числом для всех или списком, например:

```sh
./build/smart-flowers --flowers 3 --dry-rates 1,2,3 --gardeners 2 --speeds 1,2
./build/smart-flowers --config configs/ordinary.conf --delay-ms 100 --duration 50
./build/smart-flowers --flowers 2 --gardeners 0
./build/smart-flowers --flowers 0
./build/smart-flowers --duration 0
```

Число потоков ограничено также ресурсами ОС: если создать поток не удалось,
программа завершится с сообщением и освободит уже созданные ресурсы.

## Что объяснить на защите

- Поток цветка увеличивает высыхание, отправляет заявку и завершает восстановление.
  Поток садовника ждёт заявку, выбирает её и выполняет полив.
- Общий мьютекс защищает состояния, заявки, счётчики и записи журнала.
  Во время ожидания или полива мьютекс освобождён, остальные участники работают.
- У каждого садовника свой семафор уведомлений. Новая заявка уведомляет
  садовников; без работы они спят, а не крутят цикл проверки очереди.
- FIFO выбирает старейшую ожидающую заявку. После выбора садовник тратит 1 мс
  на отклик и повторно проверяет заявку под мьютексом. Если её уже поливает другой садовник,
  записывается конфликт; повторного полива по этой заявке не будет.
- Высыхание приостановлено при поливе и восстановлении. Полив занимает
  `ceil(water-duration / speed)` тактов, после него высыхание равно нулю.
- Защита отсчитывается от начала последнего успешного полива. Новая попытка
  раньше конца интервала вызывает гибель; на границе разрешена. При 0 защиты нет.
- Время берётся из монотонных часов. `delay-ms` задаёт длительность такта,
  а не только задержку печати. Общего пошагового цикла и барьера нет.

Завершение: срок наблюдения, гибель всех цветов или Ctrl+C в любом режиме.
Главный поток останавливает работников, будит ожидающих садовников,
вызывает `pthread_join`, затем сохраняет итоги и освобождает ресурсы.
Незавершённые заявки остаются в итогах как `pending`/`assigned`.
Коды выхода: 0 — штатно, 130 — Ctrl+C, 2 — неправильный ввод, 1 — ошибка исполнения.

| Файлы | Назначение |
|---|---|
| src/main.c | Параметры, сигналы, запуск модели, итог и очистка |
| src/config.c и .h | Разбор и проверка параметров |
| src/model.c и .h | Потоки, синхронизация, состояния, FIFO, инварианты |
| src/io.c и .h | Запись журнала через open/write/close |
| tests/test_simulation.py | Проверка входа, журнала, конкуренции и завершения |

## Проверки

```sh
make test
make test-sanitize
```

На macOS проверка ASan/UBSan запускается без LeakSanitizer:

```sh
make test-sanitize ASAN_OPTIONS=detect_leaks=0:halt_on_error=1
```

В тестах независимо проверяются переходы состояний, FIFO, единственный владелец
заявки, баланс счётчиков, работа нескольких садовников и завершение через Ctrl+C.
На Linux пройдены 74 проверки, на macOS — 72 (две проверки `/dev/full`
пропущены). ASan/UBSan и отдельные проверки ThreadSanitizer — без диагностик.

Отчёт: `docs/REPORT.md` и `docs/REPORT.pdf`. Протоколы: `docs/validation/`.
